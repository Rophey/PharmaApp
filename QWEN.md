## Ключевые архитектурные решения

### MBRParameter — собственные значения для каждого MBR
Каждый MBR хранит **свои** значения параметров (value, tolerance, critical_deviation) в таблице `MBRParameter`. НЕ используется общая таблица `Parameter` для значений.

### EBR: две модели параметров — номинальные и фактические

#### EBRNominalParameter — «как должно быть» (5 записей, копируются из MBR)
- `nominal_value` — номинальное значение из MBRParameter.value
- `tolerance_value` — **абсолютный** допуск = nominal × (tolerance% / 100)
- `critical_value` — **абсолютное** критическое = nominal × (critical% / 100)
- FK: `ebr`, `parameter`

#### EBRActualParameter — «как на самом деле» (5 записей, заполняются в процессе)
- `actual_value` — последнее введённое значение
- `max_value` — максимум за всё время (NULL если было критическое отклонение)
- `source` — источник: `'equipment'` (авто) или `'manual'` (ручной)
- FK: `ebr`, `parameter`

**5 параметров:**
| Параметр | Источник |
|---|---|
| Усилие прессования (кН) | equipment |
| Толщина таблетки (мм) | equipment |
| Масса таблетки (мг) | equipment |
| Твёрдость таблетки (кПа) | equipment |
| Время распадаемости (мин) | manual |

**Важно:** Сравнение отклонений идёт через `diff = abs(actual_value - nominal_value)` с абсолютными `tolerance_value` / `critical_value`, а не с процентами.

### Статусы EBR
- **«В ожидании»** — технолог запустил, оператор ещё не взял партию (operator IS NULL)
- **«В работе»** — оператор начал производство
- **«Завершена»** — подписана начальником ОКК
- **«Заблокирована»** — критическое отклонение, требует решения начальника ОКК

### Пересчёт статуса EBR
При каждом обновлении любого `EBRActualParameter`:
```python
worst = 'ok'
for each of 5 params:
    diff = abs(actual - nominal)
    if diff > critical_value: worst = 'critical'; break
    elif diff > tolerance_value: worst = 'deviation'
    elif diff > tolerance_value * 0.9: worst = 'warning'

if worst == 'critical' → EBR «Заблокирована»
```
Статус EBR = **худшее** среди всех 5 параметров.

### Симулятор оборудования — реалистичная генерация
Генерирует значения **относительно номинальных параметров партии** (EBRNominalParameter):
- 88% — норма (±50% от допуска)
- 10% — предупреждение (50-90% от допуска)
- 2% — отклонение (90-100% от допуска)
- 0.5% — критическое (>100%)

**Симулятор поддерживает несколько параллельных партий** — каждая в своём потоке с thread-safe словарём `active_productions = {ebr_id: {...}}`.

При каждом показании:
- Обновляет `EBRActualParameter.actual_value` и `max_value`
- Если `actual > critical_value` → `max_value = NULL`, Deviation(critical), EBR блокируется
- Симулятор запускается оператором с заданным временем прессования (сек)
- Записывает `pressing_start_time` и `pressing_duration` на EBR для отслеживания

### Жизненный цикл EBR
1. **Технолог** создаёт EBR из MBR → статус «В ожидании», `operator=None`, создаются 5+5 параметров, 2 операции («Выбор сырья», «Работа пресса»)
2. **Оператор** выбирает партию из «Ожидают» (где `operator IS NULL`) → статус «В работе», оператор назначается, первая операция → in_progress
3. **Оператор** подтверждает «Выбор сырья» → операция completed, следующая → in_progress
4. **Оператор** вводит время прессования (сек) → запускается симулятор, записываются `pressing_start_time` и `pressing_duration`
5. **Симулятор** генерирует 4 параметра (оборудование), обновляет actual + max, проверяет отклонения
6. **Обратный отсчёт** у оператора и технолога — показывает оставшееся время пресса
7. Пресс завершил время → **«Экспертиза в ОКК»** + уведомление оператору и технологу
8. **Сотрудник ОКК** вводит время распадаемости → проверяется отклонение
9. **Начальник ОКК** видит все 10 параметров, подписывает ЭП → «Завершена»

### Операции (BatchOperation) — семантика
| Этап | Операция в БД | `current_operation_label` |
|------|---------------|--------------------------|
| EBR создан | — | Ожидание оператора |
| Оператор начал | Выбор сырья in_progress | Выбор сырья |
| Сырьё подтверждено | Работа пресса in_progress | Подготовка пресса |
| Пресс работает (по таймеру) | Работа пресса in_progress | Пресс запущен |
| Пресс завершил (время вышло) | — | Экспертиза в ОКК |
| Подписана | — | Партия завершена |

### API endpoints
- `POST /api/mbr/<id>/approve/` — утверждение MBR (JSON)
- `GET /api/mbr/<id>/` — получение данных MBR (JSON)
- `POST /mbr/<id>/new-version/` — создание новой версии
- `POST /mbr/<id>/delete/` — удаление черновика
- `POST /ebr/api/create/<id>/` — запуск партии (JSON)
- `GET /api/ebr/<id>/monitoring/` — мониторинг партии в реальном времени (JSON)
- `POST /equipment/api/machine/<id>/send-for-batch/` — отправка показаний для партии
- `POST /ebr/<id>/start-pressing/` — запуск пресса оператором (pressing_time)
- `POST /ebr/<id>/sign/` — подписание EBR начальником ОКК

### Панель оператора
- **2 вкладки:** «Ожидают оператора» (где operator IS NULL) и «Мои партии» (активные партии оператора)

- Вкладка «Мои партии»: сортировка по времени начала работы оператором (`task.started_at`) — чем позже начал, тем выше; отправленные в ОКК — ниже
- Партии исчезают из «Мои партии» после завершения работы сотрудником ОКК (AJAX-проверка каждые 5 сек)
- Обратный отсчёт пресса (обновляется каждую секунду, без перезагрузки)
- При завершении пресса таблица параметров скрывается, отображается упрощённый вид «Партия отправлена в ОКК»
- Уведомление об отправке партии в ОКК
- Сохранение активной вкладки через localStorage

### Панель сотрудника ОКК
- Список заданий контроля качества обновляется AJAX каждые 3 сек
- Модальное окно для выполнения задания (кнопка «Выполнить») — визуальный контроль + время распадаемости + комментарий
- Ввод времени распадаемости → сохраняется в EBRActualParameter (source='manual')
- После сохранения результатов EBR пересчитывает статус и отправляется на завершение (или блокировку при отклонениях)
- Система вкладок убрана — один экран со списком заданий + модальное окно

### Панель директора
- **2 вкладки:** «Отчёты» и «Статистика»
